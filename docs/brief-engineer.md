## Контекст в одном экране

VAULTLER — ежедневный минигейм на мем-токен $VLTR. Игрок жмёт CRANK, машина сутки капает
игровой `$STACK`; вернулся в 12-часовое окно — стрик и множитель растут, проспал — рейдер
скимит 15%. Топ-10 недельного борда делит призовой пул из торговых фисов. Выплаты —
**вручную, вне сайта**, кастодии нет.

Прод: https://thevaultler.fun, Vercel + Postgres + KV, всё сконфигурировано
(`/api/health` отдаёт `store: postgres`, `rateLimit: shared`, `chain: configured`).

### Инварианты — ломать нельзя ни при каких условиях

1. **Сервер — источник правды.** API не принимает от клиента ни время, ни стек, ни стрик,
   ни флаг буста.
2. Любая мутация стейта — только через `store.mutate` (лок/транзакция).
3. `settle()` идемпотентен по `lastSettleAt` — поллинг не должен раздувать стек.
4. Тир холдерского буста ставит только сервер, читая чейн, и перепроверяет **на кранке**.
   «Не смог прочитать» ≠ «баланс нулевой».
5. Наружу не отдаются internal id (`dev:uuid`, `wallet:0x…`) и адрес скрывшего кошелёк.
6. Идентичность — только из подписанного значения, проверяется в самом роуте.
7. Каждый ответ API — `no-store` (`jsonNoStore`).
8. Каждый POST проверяет происхождение (`sameOriginOk`).

Логика живёт в чистых модулях `lib/*` и покрывается тестами; роуты остаются тонкими.
Комментарии на русском, объясняют **почему**, а не «что». Все API-роуты: `runtime = "nodejs"`,
`dynamic = "force-dynamic"`.

### Что показал прод (это и есть причина задач ниже)

## 0.1 — Снапшот результатов недели (главный блокер)

**Проблема.** В `prisma/schema.prisma` нет модели результатов недели. Ранг считается на лету
как `stack - weekStartStack`, а `weekStartStack` перезаписывается внутри `settle`
(`lib/game.ts:262-276`) при первом обращении игрока после субботней полуночи. В момент
сброса **список победителей перестаёт существовать** — восстанавливать придётся вручную по
`CrankLog`, приблизительно, в споре с людьми, которым обещаны токены.

**Что сделать.**

1. Модель `WeekResult` в схеме:

   ```prisma
   model WeekResult {
     id        String   @id @default(cuid())
     weekId    Int
     identity  String              // internal id; наружу НЕ отдаётся
     address   String?             // адрес кошелька на момент закрытия, для выплаты
     rank      Int
     gain      Float               // прирост за неделю = stack - weekStartStack
     eligible  Boolean             // подтверждённый кошелёк (см. 0.4)
     payoutTx  String?             // хеш транзакции выплаты, проставляется вручную
     createdAt DateTime @default(now())

     @@unique([weekId, identity])  // идемпотентность: повторное закрытие не задваивает
     @@index([weekId, rank])
   }
   ```

2. **Запись при переходе недели.** В `settle` переход обнаруживается по
   `state.weekId !== wk.weekId`. Сама `settle` — чистая функция и в БД не пишет, поэтому:
   верни из неё признак закрытой недели (например `closedWeek: { weekId, gain } | null`),
   а запись сделай в `store.mutate` **в той же транзакции**, что и стейт — ровно так, как
   уже сделано с `CrankLog` (`lib/store.ts:41-52`). Разъехавшийся с состоянием журнал
   перестаёт быть доказательством.

3. **Хвост спящих.** Игрок, который не вернётся, свою неделю сам не закроет. Нужен
   `scripts/close-week.mjs`: проходит по `snapshot()`, для каждого игрока со старым `weekId`
   считает `gain` и пишет `WeekResult` (идемпотентно по `@@unique`). Запускается сразу
   после полуночи. Данные для него не теряются: пока игрок не сделает кранк, его
   `weekId`/`weekStartStack` остаются прошлыми.

4. `scripts/close-week.mjs --report` печатает готовый список выплат: место, адрес, доля по
   формуле `(11 − N) / 55`, сумма. Формула — в `lib/payout.ts`, не дублируй её в скрипте.

**Готово, когда:** после субботней полуночи `SELECT * FROM "WeekResult" WHERE "weekId" = …`
отдаёт полный топ прошлой недели с адресами, и повторный запуск скрипта ничего не задваивает.
Покрыто тестом на идемпотентность.

## 0.2 — Разобраться с восемью строками `1036.8`

**Проблема.** Восемь игроков имеют идентичный стек `1036.8` (ровно сутки завода) и с тех пор
не двигаются, при этом рейдер их не тронул. `advance()` (`lib/game.ts:287-315`) пропускает
и начисление, и рейд только при `machineOn = false` или `lastCrankAt = null`, а выставить
`machineOn = false` **без** среза стека штатный путь не может: рейд всегда идёт вместе со
скимом. Значит одно из двух, и это разные диагнозы:

- **тестовые записи**, созданные в обход игровой логики (тогда они не помечены `bot:` и на
  борде неотличимы от людей) → вычистить до полуночи;
- **баг ядра**, оставляющий игрока замороженным → воспроизвести тестом и починить.

**Что сделать.** Запрос к прод-БД:

```sql
SELECT identity, stack, streak, "machineOn", "lastCrankAt", "lastSettleAt",
       "weekId", "weekStartStack", "boostTier", "boostPpb", "createdAt"
FROM "Player"
WHERE stack BETWEEN 1036 AND 1037
ORDER BY "createdAt";
```

и по каждому — журнал: `SELECT * FROM "CrankLog" WHERE "playerId" = … ORDER BY at;`

Признаки: `createdAt` пачкой в одну секунду + пустой `CrankLog` = сид. Одиночные `createdAt`
с записями в журнале = баг, и тогда воспроизводи в `lib/game.test.ts`.

**Готово, когда:** написан однозначный вывод, что это; тестовые записи удалены; баг (если
это баг) закрыт регрессионным тестом.

## 0.3 — Диагностика холдерского буста

**Проблема.** Ни один игрок не стоит даже на первой ступени `HOLDER_TIERS` (0.001% эмиссии).
Вся экономика построена на цепочке «холд → ×5 → топ-10 → покупки → объём → фисы → пул», и
первое звено пустое. Причина одна из двух: ступень недостижима для реального покупателя
(ошибка калибровки, чинится в спринте 1) **или** буст молча не читается (баг, чинить сейчас).

**Что сделать.** Взять адреса игроков с ненулевым `boostPpb = 0` и сверить с чейном:

```sql
SELECT identity, "boostTier", "boostPpb" FROM "Player" WHERE identity LIKE 'wallet:%';
```

Для каждого адреса прочитать `balanceOf` и `totalSupply` контракта
`0x4CAec139dfC936a2043FE3035B0d0D59ba877613` через `NEXT_PUBLIC_RH_RPC_URL`. Ненулевой
баланс при `boostPpb = 0` — баг чтения. Проверь заодно, что `decimals` читается с контракта,
а порог сравнивается в bigint (см. NOTES.md 2026-07-25 — там это уже чинили).

**Готово, когда:** одной строкой сказано, ноль холдеров — это факт распределения или отказ
чтения. При отказе — фикс + регрессионный тест.

## 0.4 — Выплата только подтверждённым кошелькам

**Это прямое решение владельца.** Сейчас 6 из 10 мест призовой зоны занимают `kind: "anon"` —
cookie-сессии, у которых нет адреса ни на борде, ни в базе: платить физически некуда.
Хуже — такое место создаётся бесплатно в один клик в режиме инкогнито, то есть это сивил
дешевле, чем через кошельки, и лестница тиров от него не защищает вообще.

**Дизайн (важно — не «убрать анонов с борда»).**

- Аноны **остаются на борде и ранжируются как раньше**. Убирать их нельзя: они видят своё
  место, и это единственный рычаг конверсии в кошелёк.
- Каждая строка получает флаг `eligible: boolean`. Он `true`, когда у игрока есть адрес
  (`addressFromIdentity(identity) !== null`), игрок не бот и не в `BOARD_EXCLUDE`.
- **Призовая зона считается по первым 10 `eligible`**, а не по первым 10 строкам борда.
  Анон на 3-м месте виден третьим, но пул делят десять подтверждённых.
- В UI у неподтверждённой строки — пометка и призыв подключить кошелёк; у своей строки
  анона текст прямой: «you'd be #3 — connect a wallet to be eligible».
- Игрок со скрытым адресом (`hideWallet`) **eligible**: адрес есть в базе, наружу он просто
  не отдаётся. Не перепутай `kind: "wallet", address: null` (скрыл) с `kind: "anon"` (нет
  кошелька вовсе) — `displayFor` (`lib/leaderboard.ts:82-102`) их уже различает.

**Где править:** `LeaderRow` (`lib/leaderboard.ts:18-30`) — добавить `eligible`;
`buildLeaderboard` — вычислять его и класть в строки; `app/Leaderboard.tsx` — показ;
`lib/payout.ts` — список выплат строится по eligible-подмножеству.

Осторожно: имя `eligible` уже занято внутри `buildLeaderboard` (строка 113) для
отфильтрованного по `BOARD_EXCLUDE` снапшота — переименуй локальную переменную, иначе
получится тихая путаница двух разных «eligible».

**Готово, когда:** `/api/leaderboard` отдаёт `eligible` в каждой строке; UI показывает
призовую зону только по подтверждённым; тест в `lib/leaderboard.test.ts` покрывает случаи
аноним / кошелёк / скрытый кошелёк / бот / исключённый.

## 4.1 (C1) — подписанные результаты недели

**Зачем.** Сейчас против спора «у меня было больше» у нас только добросовестность. Подпись
превращает спор в проверку.

- **Подпись асимметричная (Ed25519 через `node:crypto`), не HMAC.** HMAC проверяет только
  тот, кто знает секрет, то есть мы сами — для доказательства третьей стороне бесполезен.
- **Отдельный `RESULTS_SIGNING_KEY`, не `SESSION_SECRET`.** Разное назначение и разный срок
  жизни; публикация публичной части не должна давать ни одной зацепки к сессиям.
- **Наружу идёт `publicId`, а не `identity`** — инвариант 5. И это не хеш от `identity`:
  адреса кошельков публичны, значит хеш перебирается за минуты и деанонимизирует тех, кто
  скрыл адрес. `publicId` — случайное стабильное значение, хранится в БД рядом с игроком.
- **Сериализация детерминированная** (сортировка ключей, фиксированная точность чисел) —
  иначе подпись не воспроизводится и вся затея бессмысленна.
- `GET /api/results/:weekId` отдаёт подписанный документ; публичный ключ — на постоянной
  странице сайта.

**Готово, когда:** сторонний скрипт из 20 строк, зная только публичный ключ и ответ API,
подтверждает подпись; тест ловит попытку подписать документ с `identity` внутри.

## 4.2 (C2) — ончейн-якорь недели

**Зачем.** Независимый timestamp: после якорения мы физически не можем переписать
победителей задним числом, и это проверяет любой через эксплорер.

- В calldata — версия формата, `weekId` и sha256 подписанного документа из 4.1. Контракт не
  нужен: достаточно self-transaction. На L2 стоит доли цента.
- **Отдельный кошелёк-нотариус**, только для якорения, с минимальным газом. Не кошелёк
  выплат и тем более не кошелёк с бэгом команды: ключ живёт в env скрипта, и компрометация
  нотариуса не должна стоить ничего, кроме мусорных якорей.
- `scripts/anchor-week.mjs` запускается сразу после `close:week`. Хеш и ссылка на транзакцию
  сохраняются и показываются на `/payouts` рядом с выплатами.

**Готово, когда:** для закрытой недели на `/payouts` есть ссылка на транзакцию, а хеш из
calldata сходится с sha256 документа, отданного `/api/results/:weekId`.

## 4.3 (C3) — открытый датасет и «пересчитай нас сам»

**Зачем.** Самая сильная форма инварианта «сервер — источник правды»: мы не просим верить,
мы даём инструмент проверки.

- `GET /api/history` — псевдонимный журнал кранков (`publicId`, время, стек, `lostToRaid`,
  тир буста) плюс закрытые недели. Адрес отдаётся только у тех, кто его не скрыл.
- **Пагинация с первого дня.** Журнал растёт бессрочно; без неё повторим баг `snapshot()`,
  только на эндпоинте, который специально зовут роботы.
- `scripts/verify.mjs` — эталонный верификатор: берёт датасет, прогоняет через настоящие
  `settle`/`buildLeaderboard` (не через копию логики) и сверяет с опубликованным
  `WeekResult`. Расхождение — красный тест.

**Готово, когда:** `verify.mjs` зелёный на живых данных прода, и отдельный тест доказывает,
что ни один ответ `/api/history` не содержит `dev:`, `wallet:`, `bot:` и адресов игроков с
`hideWallet`.

## 4.4 (C4) — merkle-распределитель выплат

**Только когда недельный пул перестанет измеряться десятками долларов.** Пока пул маленький,
три ручных перевода дешевле и безопаснее контракта.

- Контракт **не принимает депозиты от игроков**. Владелец переводит уже начисленный пул и
  публикует root; игроки клеймят по доказательству. Кастодии не появляется.
- **Не писать свой** — брать проверенную реализацию merkle distributor и менять минимум.
- Невостребованное через N недель возвращается владельцу (иначе средства блокируются
  навсегда, а `no treasury` превращается в ложь наоборот).
- Root считается из тех же `WeekResult`, что и подпись 4.1 — одна истина, а не вторая
  реализация подсчёта, способная разойтись с бордом.
- Перед деплоем обязательно: Slither, тесты Foundry (включая попытку двойного клейма и
  клейма с чужим доказательством), прогон субагента `smart-contract-auditor`, тестнет.

**Готово, когда:** на тестнете полный цикл — пополнение, публикация root, клейм каждым из
топа, отказ двойного клейма, возврат остатка — и отчёт аудита приложен.

## 4.5 (D1) — генератор лора из журнала кранков

Ежедневный контент без ручной работы: агент читает `CrankLog` за сутки и пишет 2–3 поста в
лоре вестерна («рейдер забрал 187 у старателя, опоздавшего на 11 минут»). Это снимает с CM
ежедневную рутину и делает ритуал независимым от того, есть ли у человека время.

**Жёсткие границы, не обсуждаются:** у агента доступ только на чтение агрегатов; он не
касается ключей, стейта игры и выплат; он не постит сам и не отвечает игрокам — отдаёт
черновик, публикует человек. Правило «команда никогда не пишет первой» абсолютно, и агент
его нарушит на третий день, если дать ему такую возможность.

**Готово, когда:** черновики генерируются по расписанию, ни один не содержит адресов и
internal id, и в них нет ни одной цифры, которой нет в базе.

## Постоянные требования

- **Перед пушем** — `npm run check:secrets` (подключается хуком:
  `git config core.hooksPath .githooks`). Репозиторий приватный, но секреты в историю

  теста не принимается.
- **Тест не должен строить входные данные сам.** Однажды 77 тестов пропустили баг, потому
  что подставляли свой ASCII-текст вместо реальной константы `SIWE_STATEMENT` — проверяли
  себя, а не продукт (NOTES.md 2026-07-25).
- **Next.js здесь 16-й**, middleware заменён на `proxy.ts`. Перед правкой фреймворочных
  вещей читать `node_modules/next/dist/docs/`.
- `docs/deployment.md` разошёлся с продом (утверждает, что `DATABASE_URL`, `KV_*` и конфиг
  сети не заданы — они заданы). Привести в соответствие: документ, которому нельзя верить,
  опаснее отсутствующего.
- Не автоматизировать выплаты пула — это действие владельца, а не кода. Задача инженера —
  дать точный список и доказательства, а не отправить токены.
