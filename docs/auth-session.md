# Идентичность: сессия, вход кошельком, профиль

`lib/session.ts` · `lib/auth.ts` · `lib/http.ts` · `proxy.ts` ·
`app/api/auth/*` · `app/api/profile/route.ts` · `app/components/ConnectButton.tsx`

## Две ступени идентичности

| | Анонимная сессия | Кошелёк |
|---|---|---|
| id | `dev:<uuid>` | `wallet:<addr lowercase>` |
| откуда | `proxy.ts` минтит при первом визите | подтверждённая SIWE-подпись |
| играть | да | да |
| ник | **нет** (403) | да |
| холдерский буст | нет | да, ступень по доле в эмиссии |
| «один аккаунт» | нет (кука сбрасывается) | да: один кошелёк = один аккаунт |

Играть без кошелька можно намеренно — это снижает порог входа. Всё, что связано с
реальными наградами и публичной личностью, требует кошелька.

## Подписанная cookie-сессия

Значение `vaultler_sid` = `<payload>.<base64url(HMAC-SHA256(payload, SESSION_SECRET))>`,
где `payload = <версия>:<issuedAt мс>:<id>`.
Клиент не знает секрет → не подделает чужой id. Сравнение подписи —
за константное время (`safeEqual`), чтобы не утекала информация через тайминги.

Версия и время выпуска — не украшение:

| поле | зачем |
|---|---|
| `SESSION_VERSION` | аварийный рубильник: поднять версию = разлогинить всех разом, не трогая `SESSION_SECRET` (смена секрета ломает и всё остальное) |
| `issuedAt` | TTL 30 дней. Раньше payload был голым id: утёкшая cookie (общий компьютер, логи прокси) действовала год и не отзывалась ничем |

Сессия продлевается скользящим окном: если cookie старше 7 дней, `proxy.ts` переподписывает
её на текущий момент. Активный игрок не разлогинивается, брошенная сессия тухнет сама.
Cookie «из будущего» (часы уехали или payload подкручен) отвергается.

Реализовано на Web Crypto (`crypto.subtle`), а не на `node:crypto`: модуль должен
работать и в Edge (`proxy.ts`), и в Node (роуты) — один источник правды.

**`SESSION_SECRET` в проде обязателен** (≥16 символов), иначе приложение намеренно падает.
Дефолт `dev-insecure-secret-change-me` публично известен из репозитория: зная его, любой
подделал бы cookie и выдал себя за чужого игрока, включая кошельковые аккаунты в топе
борда. Проверка ленивая (на использовании, не на импорте) — иначе падал бы `next build`,
где рантайм-секрета ещё нет.

## Почему cookie ставится в `proxy.ts`, а не через fetch

Cookie сессии выставляется на **навигационном** ответе. Причины:
1. некоторые браузеры (и preview-sandbox, в котором проект отлаживался) не сохраняют
   `Set-Cookie` из fetch-ответов — навигационные куки сохраняются везде;
2. чинит гонку двойного минта идентичности при React StrictMode в dev.

Идентичность прокидывается в роут заголовком `x-vaultler-id` (proxy → route).
Роут читает его через `resolveIdentity()`, с фолбэком на cookie для прямых обращений к `/api`.

**Заголовок передаётся подписанным, и роут проверяет подпись сам.** Раньше `resolveIdentity`
доверял заголовку как есть: защитой служило то, что `proxy.ts` затирает клиентский
одноимённый заголовок. Это работает, пока proxy отработал — а предположение ломается от
правки `matcher`, от бага обхода middleware во фреймворке (был CVE-2025-29927: один
заголовок отключал middleware целиком) и при прямом вызове роута на самохостинге. Цена
ошибки — полный захват любого аккаунта одним

```bash
curl -H "x-vaultler-id: wallet:0xЖЕРТВА" https://…/api/crank
```

включая кошельки из топа борда, который делит реальные токены. Документация Next прямо
предупреждает, что proxy — не механизм авторизации. Теперь подделка требует `SESSION_SECRET`.
Регрессия закрыта в `lib/http.test.ts` и в `scripts/test-auth.mjs`.

## Вход кошельком: SIWE / EIP-4361

Используются аудированные примитивы `viem/siwe` — своих парсеров сообщений нет.

```
клиент                                   сервер
──────                                   ──────
GET /api/auth/nonce ───────────────────► generateSiweNonce()
                                         nonce → httpOnly cookie (TTL 5 мин) + тело
createSiweMessage({domain, address,
  statement, uri, chainId, nonce,
  issuedAt, expirationTime})
signMessageAsync(message)  ← кошелёк
POST /api/auth/verify ─────────────────► 1) domain == expectedAuthDomain
  { message, signature }                 2) nonce == cookie
                                         3) не истекло (expirationTime)
                                         4) verifyMessage(address, message, signature)
                                         → identity = wallet:0x…, тир буста из чейна
                                         → cookie сессии, nonce гасится
```

Что даёт каждая проверка:
- **домен** — анти-фишинг и replay на чужом сайте: кошелёк показывает пользователю домен
  из сообщения, а наш сервер примет подпись только со своим доменом. В проде домен пинится
  через `AUTH_DOMAIN`, потому что заголовок `Host` можно подделать;
- **nonce** — одноразовый, лежит в httpOnly-cookie и гасится при verify: перехваченную
  старую подпись переиспользовать нельзя;
- **срок 5 минут** (`SIWE_TTL_MS`) — пойманная подпись быстро протухает;
- **подпись** — собственно доказательство владения кошельком.

Плюс верхние границы на входе: сообщение ≤2000 символов, подпись строго `0x[hex]+`,
rate-limit 30/мин на IP.

**Модель угроз входа:** мы не шлём транзакций и не просим `approve` — только читаем
подпись сообщения и публичный баланс. Через этот флоу нечего задрейнить, приватные ключи
не участвуют. Текст подписи (`SIWE_STATEMENT`) прямо говорит это пользователю:
«no transaction, no gas, no access to your funds».

Бэклог: **ERC-1271** (смарт-контрактные кошельки) — требует рабочего RPC.

## Профиль: ник и приватность адреса

Правила ника (`lib/profile.ts`):
- 3–16 символов, только `[a-zA-Z0-9_]`;
- нельзя резервные слова (`anon`, `admin`, `team`, `vaultler`, `bot`, `raider`…) —
  анти-импертонация;
- нельзя начинать с `0x` — иначе ник маскируется под адрес кошелька, а на борде
  рядом стоят настоящие адреса;
- уникальность глобальная, без учёта регистра (см. `docs/data-store.md`).

Приватность адреса:
- по умолчанию адрес **открыт** — прозрачность важнее: люди хотят проверить,
  реальным ли кошелькам уходят выплаты, и ходят по ссылке в explorer;
- игрок может скрыть — тогда `leaderboard.address = null`, адрес наружу **не уходит вообще**,
  ярлык = ник или «anon»;
- в UI честно сказано, что скрытие не прячет on-chain историю (это невозможно) —
  только наш показ.

## Rate-limit по эндпоинтам

`lib/ratelimit.ts`, ключ — первый IP из `X-Forwarded-For` (для кранка — идентичность).
Все лимитеры асинхронные: под ними может быть сетевой вызов в Redis.

| Лимитер | Бюджет | Где |
|---|---|---|
| `allowCrank` | 1 / сек на **идентичность** | `/api/crank` |
| `allowAuth` | 30 / мин на IP | `/api/auth/verify` |
| `allowNonce` | 40 / мин на IP | `/api/auth/nonce` |
| `allowProfile` | 30 / мин на IP | `/api/profile` |

Бюджеты разведены, чтобы смена ника не съедала лимит логина.

**Где живут счётчики.** При заданных `KV_REST_API_*` — в общем Redis (`lib/kv.ts`), один
на все инстансы. Иначе — в памяти процесса, и тогда лимит обходится размазыванием
запросов: на serverless каждый запрос может попасть в свежий инстанс с пустым счётчиком.
Что активно сейчас, видно в `/api/health` → `rateLimit`.

Кранк лимитируется через `SET NX EX 1` (атомарный «не чаще раза в секунду»), окна —
через `INCR`+`EXPIRE` с номером окна в ключе. Окно фиксированное, а не скользящее: обе
команды атомарны и укладываются в один round-trip. Плата — на стыке окон теоретически
проходит до 2× лимита; для анти-флуда это заложено в бюджеты.

Если Redis недоступен, лимитер **не роняет запрос**, а откатывается на счётчик в памяти
и пишет предупреждение (не чаще раза в минуту). Это осознанный размен: лимитер защищает
от флуда, а не от денежной операции — сам кранк валидируется фазой в `lib/game.ts`,
и там обойти ничего нельзя.
