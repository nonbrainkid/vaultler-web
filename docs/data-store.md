# Хранилище данных

`lib/store.ts` (интерфейс) · `lib/store-file.ts` (dev) · `lib/store-prisma.ts` (прод) ·
`prisma/schema.prisma` (схема).

## Выбор реализации

```
DATABASE_URL задан        → PrismaStore (Postgres)
DATABASE_URL пуст, dev    → FileStore (.data/players.json)
DATABASE_URL пуст, prod   → падаем с внятной ошибкой
```

Последнее — намеренно: на Vercel файловая система эфемерна, файловый стор молча терял бы
стейт игроков (и их место в борде, который делит реальные токены). Лучше явный отказ
при старте, чем тихая потеря данных. Реализация кэшируется в модульном синглтоне.

## Интерфейс `Store`

| Метод | Назначение | Атомарность |
|---|---|---|
| `read(identity, now)` | прочитать стейт (или `initialState`) **без записи** | не нужна |
| `mutate(identity, now, fn)` | read-modify-write чистой функцией из `lib/game` | лок / транзакция |
| `snapshot()` | все игроки со стейтами — для борда | нет |
| `setProfile(identity, now, patch)` | ник + приватность, с проверкой уникальности | глобальная сериализация |
| `saveWeekResults(records)` | результаты завершённой недели | одна транзакция на всю неделю |
| `weekResults(weekId)` | кто и с каким местом закончил неделю | нет |

### Результаты недели фиксирует сам `mutate`

Помимо стейта и журнала кранков, `mutate` записывает **результат завершённой недели**,
если `fn` перевела игрока через субботнюю границу (`closedWeekOf`, `lib/week-results.ts`).
Делает это реализация стора, а не вызывающий код — по той же причине, по которой перевод
недели живёт внутри `settle`: через `mutate` проходят все пути записи, и любой новый роут
иначе мог бы «забыть» зафиксировать неделю.

Почему это вообще нужно: ранг на борде считается как `stack - weekStartStack`, а база
перезаписывается при первом же обращении игрока после полуночи. Без записи в момент
перехода список победителей **исчезает ровно тогда, когда по нему надо платить**.
Прирост берётся как разница двух баз (`next.weekStartStack - prev.weekStartStack`) —
то есть из того же следа, который `settle` уже оставляет, без второй реализации подсчёта,
способной разойтись с бордом.

Место (`rank`) при этом остаётся `null`: оно свойство всей таблицы, а не игрока. Ранги и
доли пула проставляет финализация — `POST /api/admin/close-week` (`docs/api.md`), она же
досчитывает тех, кто после субботы так и не вернулся.

## Почему `mutate` — атомарный

Без лока два одновременных кранка читают один стейт и оба начисляют стек — классическая
гонка, из которой делается накрутка (открыть две вкладки и жать одновременно).

- **FileStore**: единая очередь (`withQueue`) — **все** операции стора строго
  последовательны. Раньше лок был per-identity, но любая запись перезаписывает файл
  целиком: параллелизм между игроками ничего не давал, зато позволял потерять запись
  (пока A персистит, операция B перечитывала файл ещё без изменений A и затирала их).
  Один поток проще и заведомо корректен; настоящие построчные локи есть там, где они
  нужны — в Prisma-сторе для прода.
- **PrismaStore**: `prisma.$transaction` + `SELECT 1 … FOR UPDATE` на строку игрока,
  затем `upsert`. Строка лочится на время транзакции.

`GET /api/state` намеренно **не** использует `mutate`: поллинг раз в 2.5 с создавал бы
транзакцию на каждый тик, а стек и так детерминирован из таймстемпов. Персист — на кранке.

## Уникальность ников

Ник уникален глобально **без учёта регистра**: хранится `nickname` (как показывать)
и `nicknameKey` (lowercase, `@unique`).

Гонка «два игрока разом занимают один ник» закрыта на обоих сторах:
- **Prisma**: `findFirst` по `nicknameKey` — быстрый путь; если оба прошли проверку,
  unique-констрейнт отвергает второго, ошибка `P2002` перехватывается и превращается
  в чистый `409 nickname_taken` вместо 500;
- **FileStore**: очередь стора сериализует все операции, поэтому проверка «ник свободен»
  видит актуальный файл целиком и между проверкой и записью никто ник занять не успевает.

Покрыто `lib/profile.test.ts` и e2e `scripts/test-profile.mjs` (в нём есть отдельный
кейс на гонку).

## Схема БД

```prisma
model Player {
  id           String   @id @default(cuid())
  identity     String   @unique   // "wallet:0x…" | "dev:uuid" | "bot:name"
  stack        Float    @default(0)
  streak       Int      @default(0)
  lastCrankAt  BigInt?            // epoch ms
  lastSettleAt BigInt             // epoch ms
  machineOn    Boolean  @default(false)
  boostTier    Int      @default(0)   // ступень HOLDER_TIERS (0 — не холдит)
  boostPpb     Int      @default(0)   // доля в эмиссии (ppb) на момент чтения чейна
  weekId         Int   @default(0)    // неделя, к которой отнесён текущий прогресс
  weekStartStack Float @default(0)    // база недели: ранг = stack − weekStartStack
  nickname     String?
  nicknameKey  String?  @unique   // lowercase — ключ уникальности
  hideWallet   Boolean  @default(false)
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt
  crankLogs    CrankLog[]
  @@index([stack])                // сортировка борда
}

model CrankLog {                  // аудит кранков: анти-чит и разбор споров
  id String @id @default(cuid())
  playerId String
  at BigInt          // серверный epoch ms
  ok Boolean         // прошёл ли валидацию фазы
  phase String       // фаза на момент попытки (до завода)
  streak Int
  stack Float        // стек ПОСЛЕ кранка — точка отсчёта при разборе
  lostToRaid Float?  // ским рейдера в этом же settle; null — рейда не было
  @@index([playerId, at])
}

model WeekResult {                  // итоги завершённой недели — по ним платят
  id String @id @default(cuid())
  weekId   Int
  identity String                   // internal id; наружу не отдаётся
  address  String?                  // адрес для выплаты; null — игрок без кошелька
  gain     Float   @default(0)      // прирост за неделю, по нему ранжируют
  rank     Int?                     // место в деньгах; null — вне денег / не финализирована
  eligible Boolean @default(false)  // подтверждённый кошелёк
  share    Float   @default(0)      // доля пула (0…1), перенормированная на число мест
  payoutTx String?                  // хеш выплаты, вписывается вручную
  @@unique([weekId, identity])      // идемпотентность повторного закрытия
  @@index([weekId, rank])
}
```

`BigInt` для времени: epoch ms не влезает в `Int`. Конвертация в/из `number` — в
`toState`/`toWrite` (`store-prisma.ts`).

### Журнал кранков

Пишется в **той же транзакции**, что и стейт игрока: иначе падение между двумя записями
развело бы журнал с тем, что он описывает, и он перестал бы быть доказательством.
Механика — необязательный четвёртый аргумент `mutate`:

```ts
store.mutate(identity, now, fn, (outcome) => CrankAudit | null)
```

`null` — не писать. Роут `/api/crank` журналирует **только успешные** кранки: отклонённые
(фаза `winding`) стейт не меняют, спорить о них не о чем, а клиент, поллящий кранк, при
лимите 1/сек нагенерил бы до 86 400 строк в сутки на игрока.

Файловый стор аргумент принимает и игнорирует — он только для локальной разработки,
где реальных призов и споров не бывает.

### Свежесть файлового стора (закрытая ловушка dev)

Источник правды — **файл**, а не копия в памяти экземпляра. Перед каждой операцией
`FileStore` сверяет отпечаток файла (`mtime` + размер) и перечитывает его, если файл
изменился со стороны. Обычный поллинг обходится одним `stat`.

**Что было до этого (баг, стоивший игры).** Файл читался один раз (`ensureLoaded`), дальше
экземпляр жил своей копией. За сессию правок Next-HMR создаёт несколько экземпляров модуля
`lib/store.ts`, у каждого свой синглтон `_store` и своя копия данных, — и роуты расходились
в показаниях. На игре это выглядело как поломка петли: `POST /api/crank` заводил машину и
писал файл, а `GET /api/state` из другого экземпляра продолжал отвечать
«machine is off, стек 0». Игрок жал CRANK, видел стакание ровно до первого поллинга
(~2.5 с) и решал, что игра сломана. Лечилось перезапуском dev-сервера — то есть не
лечилось, а возвращалось при следующей правке.

Покрыто тестами: `lib/store-file.test.ts` (кросс-экземплярная свежесть, внешняя правка
файла сидером, отсутствие затирания чужих записей, битый JSON, удалённый файл).

Записи старого формата приводятся к текущей схеме через `hydrateState` (`lib/game.ts`):
неизвестный тир трактуется как «буста нет», легаси `boost: true` поднимается только до
первой ступени.

Остаточное ограничение: отпечаток не заметит двух записей в одну и ту же миллисекунду с
одинаковым размером файла. Для dev-стора это несущественно (в проде — `PrismaStore`,
который вообще не держит состояние в памяти: каждое чтение идёт в Postgres).

## Форматы идентичности

| Префикс | Откуда | Ник разрешён | Адрес на борде |
|---|---|---|---|
| `dev:uuid` | анонимная cookie-сессия из `proxy.ts` | нет (403) | нет, ярлык «anon» |
| `wallet:0x…` | подтверждённая SIWE-подпись | да | да, если не скрыт |
| `bot:name` | `scripts/seed-bots.mjs` (только dev) | — | нет, тег `test` на борде |

Сырая идентичность наружу не отдаётся никогда — только производный ярлык
(`displayFor` в `lib/leaderboard.ts`).

## Локальные данные

`.data/players.json` — dev-персист, **в `.gitignore`** и в списке запретных файлов
аудита секретов. Файловый стор кэширует данные в памяти: после ручной правки файла
или сидинга ботов dev-сервер надо перезапустить.

## Известные ограничения

- `snapshot()` тянет **всех** игроков и считает `settle` каждому в памяти. На тысячах
  игроков нужна пагинация или материализованный топ (запись `stack` при кранке + `ORDER BY`).
- Прогон миграций: сейчас `prisma db push` (см. `docs/deployment.md`), полноценных
  миграций нет — до первого прода это дешевле.
