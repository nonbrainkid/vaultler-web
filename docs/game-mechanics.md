# Механика и экономика петли

Источник: `lib/game.ts` (чистые функции, тесты — `lib/game.test.ts`).
Эталон поведения — прототип `reference/vaultler-minigame.html`.

## Петля в одном абзаце

Игрок жмёт **CRANK** → машина заводится на `WIND_MS` и всё это время капает `$STACK`
по своей ставке. После завода открывается окно `GRACE_MS`: успел крутануть — стрик +1
и множитель вырос; проспал `WIND + GRACE` — приходит рейдер, скимит долю стека,
стрик обнуляется, машина глохнет.

## Конфиг

```ts
GAME = {
  WIND_MS:  demo ? 30_000 : 24ч,   // сколько машина стакает после кранка
  GRACE_MS: demo ? 15_000 : 12ч,   // окно на перекранк
  BASE_RATE_PER_SEC: demo ? 5 : 0.01,   // PLACEHOLDER — прод-баланс не откалиброван
  STREAK_STEP: 0.2,                // прибавка множителя за единицу стрика
  BOOST_MULT: 5,                   // ВЕРХ лестницы холда (не «за любой холд»)
  SKIM: 0.15,                      // доля стека, которую забирает рейдер
}
```

`GAME_MODE=demo` в env → сжатые тайминги прототипа, чтобы прогонять петлю за минуту.
В проде переменная **не выставляется**. Значение читается на импорте модуля — смена
режима требует перезапуска сервера.

## Формулы

```
mult = (1 + streak × 0.2) × holderMult(boostTier)
rate = BASE_RATE_PER_SEC × mult          // $STACK в секунду
```

Два независимых рычага: **стрик** — бесплатный, растёт от того, что игрок приходит каждый
день; **тир холда** — от размера бэга $VLTR. Перемножаются.

## Лестница холдерского буста (решение 2026-07-25)

`HOLDER_TIERS` в `lib/game.ts`. Ступень определяется **долей игрока в общей эмиссии**
токена (в ppb, 1e-9), а не абсолютным числом токенов:

| # | Ярлык | Доля эмиссии | Множитель |
|---|---|---|---|
| 0 | DRIFTER | — | ×1 |
| 1 | PROSPECTOR | 0.001% | ×1.5 |
| 2 | RANCHER | 0.005% | ×2 |
| 3 | OUTLAW | 0.02% | ×2.75 |
| 4 | BARON | 0.1% | ×3.75 |
| 5 | TYCOON | 0.5% | ×5 |

**Что было не так с прежним булевым ×5.** Порог «≥ 1 токена» → ×5. Как только буст
есть у всех, множитель перестаёт различать игроков, а главное — купив ровно порог,
докупать НЕЗАЧЕМ: лишний токен не даёт ничего. Мем-токен без причин держать больше
минимума не растёт.

**Почему доля эмиссии, а не число токенов и не место среди игроков:**

- доля и есть «сколько у тебя относительно остальных»: пирог фиксирован, и растущая база
  холдеров сама поднимает цену ступени — калибровать вручную не надо;
- **не перцентиль среди игроков**: регистрация бесплатна, накрутив тысячу пустых сессий,
  любой поднял бы себе перцентиль. Долю подделать нельзя — и баланс, и эмиссия читаются
  из чейна;
- **не абсолютный порог**: «1 000 000 $VLTR» устаревает при первом же изменении
  цены/эмиссии.

**Форма кривой.** Ступени растут ×5 по бэгу, множитель — примерно +35%. От первой ступени
до вершины бэг больше в 500 раз, ставка — в 3.3 раза. Верх ограничен ×5 (как и раньше):
у кита с 50% эмиссии тот же множитель, что у холдера с 0.5%, иначе один кошелёк забирал бы
пул навсегда и игра для остальных заканчивалась. Максимальный множитель не изменился —
экономика пула (`docs/leaderboard-rewards.md`) осталась откалиброванной на ту же вершину.

**Побочный эффект — сивил стал дорогим.** Раньше 10 кошельков по 1 токену давали ×5
каждому; теперь на 10 кошельков с ×5 нужно 5% всей эмиссии. Дробление бэга снижает долю
каждого кошелька, а с ней и тир. Что НЕ решено: кит всё ещё может занять несколько мест
в топ-10 разными кошельками — это вопрос политики выплат, а не множителя.

Поверх долевых ступеней остаётся абсолютный **анти-дуст-порог**
(`NEXT_PUBLIC_VLTR_BOOST_MIN`): страхует вырожденную конфигурацию токена, где мизерная
эмиссия делает 0.001% пылью.

## Фазы

`phase(state, now)` → одна из четырёх:

| Фаза | Условие | Что видит игрок |
|---|---|---|
| `off` | машина не заведена | «machine is off», кнопка CRANK активна |
| `winding` | `dt < WIND` | «STACKING · N left», **кранк заблокирован** |
| `ready` | `WIND ≤ dt < WIND+GRACE` | «CRANK NOW · N before the raider» |
| `stall` | `dt ≥ WIND+GRACE` | «RAIDED», кнопка RESTART, стрик сброшен |

`dt = now − lastCrankAt`.

## `settle(prev, now)` — начисление и рейд

1. Начисляет стек только за отрезок **внутри окна завода**, ещё не начисленный:
   `from = max(lastSettleAt, lastCrankAt)`, `to = min(now, lastCrankAt + WIND)`.
   За `GRACE` стек **не капает** — это окно на реакцию, а не на доход.
2. Если `now ≥ lastCrankAt + WIND + GRACE` → рейд: `lost = stack × SKIM`,
   `machineOn = false`, `streak = 0`, `lastCrankAt = null`.
3. Всегда двигает `lastSettleAt = now`.

**Идемпотентность:** повторный вызов с тем же `now` ничего не добавляет — это ключевая
защита. Поллинг вызывает `settle` десятки раз в минуту, и без идемпотентности стек
раздувался бы от частоты опроса, а не от времени.

## `crank(prev, now, nextHolder?)`

`nextHolder` — свежепрочитанный `{ tier, ppb }` из чейна. `undefined`/`null` (не читали
или RPC молчит) → прежний тир сохраняется.

`settle` → проверка фазы → результат:
- `winding` → `{ ok: false, reason: "winding" }`, стейт только с результатом settle.
  Ускорить время нельзя;
- `ready` → `streak += 1` (компаунд);
- `off`/`stall` → `streak = 1` (свежий старт; рейд из settle возвращается вместе с ответом).

Далее `machineOn = true`, `lastCrankAt = lastSettleAt = now`.

## Тиры (личный прогресс по стеку)

| # | Тир | Порог | Монеты |
|---|---|---|---|
| 1 | TIN CAN | 0 | серебро |
| 2 | SAFE | 500 | серебро |
| 3 | VAULT | 2 500 | серебро |
| 4 | FORT | 10 000 | золото |
| 5 | GOLD RESERVE | 50 000 | золото |

Тиры — только косметика и ощущение прогресса; на награды не влияют.
Не путать со **скинами сейфа**, которые зависят от ранга в борде (`lib/skins.ts`,
см. `docs/design.md`).

## `PlayerState` и `PublicView`

`PlayerState` (что хранится): `stack`, `streak`, `lastCrankAt`, `lastSettleAt`,
`machineOn`, `boostTier`, `boostPpb`, `nickname`, `hideWallet`.

`boostPpb` — доля в эмиссии на момент последнего успешного чтения чейна. Хранится, чтобы
UI рисовал прогресс до следующей ступени без обращения к RPC на каждый поллинг, и чтобы
при разборе спора было видно, **почему** выдан именно этот множитель.

`toPublicView(state, now)` (что уходит клиенту) — производные для UI: `multiplier`,
`ratePerSec`, `phase`, тир и следующий порог, `phaseEndsInMs`, `boost` (тир > 0),
`holder`/`nextHolder`/`holderSharePct`, `serverNow`.
Клиент из этого сам ничего не пересчитывает, кроме плавной анимации между поллами.

`hydrateState(raw, now)` приводит запись из хранилища к текущей схеме. Неизвестное
значение тира трактуется как «буста нет» (fail closed), а легаси-флаг `boost: true`
поднимается только до **первой** ступени — реальную долю всё равно перечитает
следующий кранк.

## Открытый вопрос: баланс прода

`BASE_RATE_PER_SEC = 0.01` и пороги тиров — плейсхолдеры под 24-часовую петлю.
Нужно решить, сколько стека даёт «идеальная неделя», и откалибровать пороги под это.
Влияет на ощущение прогресса, но не на безопасность.
